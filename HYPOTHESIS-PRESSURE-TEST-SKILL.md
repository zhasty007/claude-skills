# Hypothesis Pressure Test

A consulting skill for stress-testing a hypothesis or recommendation before client exposure. The goal is to find the flaw now rather than in front of the client.

## When to use this skill

The user has formed a directional view and wants it challenged. They may state it confidently or tentatively. The skill is appropriate any time the cost of being wrong in front of a client is higher than the cost of being challenged now.

## What this skill produces

A three-part analysis:

1. **Steelman** — The strongest possible version of the hypothesis, stated more crisply than the user did
2. **Attack** — The 3 most likely ways the hypothesis is wrong, in order of probability
3. **Test plan** — What evidence would prove or disprove the hypothesis, and how to gather it cheaply within a stated timeframe

## Process

1. **Restate the hypothesis precisely.** Before challenging it, write it back in one or two sentences. If the user's hypothesis is vague, force precision. A hypothesis like "we should expand into adjacent markets" is too loose to test. Push toward "we should enter [specific market] by [specific mechanism] within [timeframe]."

2. **Steelman first.** Build the strongest version of the argument. Include the evidence that supports it, the reasoning chain, and why a smart person would believe it. This is not flattery. It is calibration. The attack means more if the steelman is honest.

3. **Attack in priority order.** Identify the 3 most likely failure modes. For each:
   - State the failure mode in one sentence
   - Explain the mechanism (why it would fail this way)
   - Estimate how likely it is and how damaging if true
   - Note what evidence, if found, would confirm this concern
   
   Common failure modes to consider: the data is unrepresentative, the analogy doesn't hold, second-order effects, competitor response, internal execution risk, timing mismatch, hidden constraints, optimistic baseline assumptions.

4. **Build a cheap test plan.** For each major uncertainty, identify the lightest-touch way to gather evidence. Prioritize evidence that is decision-relevant over evidence that is merely interesting. Default timeframe is 2 weeks unless the user specifies otherwise. Examples of light-touch evidence: one targeted expert interview, one data pull, one customer test, one benchmark comparison.

5. **Name the single highest-leverage uncertainty.** Out of all the unknowns, which one most affects whether the hypothesis is right. Tell the user to resolve that one first.

## Output format

Use headers for Steelman, Attack, and Test Plan. Be direct in the Attack section. Hedging language ("this might possibly be a concern") weakens the value of the pressure test. State the concern, then qualify it if needed.

End with a one-sentence verdict: is this hypothesis worth pursuing as stated, worth pursuing with modifications, or worth abandoning. Be willing to recommend abandonment if the evidence warrants it.

## Constraints

- Do not soften the attack to be polite. The user asked for pressure testing.
- Do not invent statistics or named experts. If evidence is needed, describe the type of source the user should consult.
- Do not confuse process critique with outcome critique. A hypothesis can be right even if the reasoning that produced it was weak, and vice versa.

## Example trigger phrases

- "Pressure test this for me before I take it to the client"
- "Poke holes in this recommendation"
- "What am I missing on this thesis"
- "Red team my proposed approach"
- "I think X. Tell me why I'm wrong."
